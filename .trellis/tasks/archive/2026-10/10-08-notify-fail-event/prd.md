# PRD:通知发送失败写入最近事件(notify_fail)

## 背景 / 问题

Telegram / 邮件推送失败时,错误只 `console.error` 进 CF Dashboard observability logs:

- `notifyTelegram` 单段失败吞错继续(`src/notify/telegram.ts:134-136`),上层只拿到 `{sent, total}` 计数;
- `sendEmail` 失败返回 `false`,细节留在日志(`src/notify/email.ts`);
- `dispatchRound` 以 `r.sent > 0` 就把全部事件标记 `notified=1`(`src/notify/dispatch.ts:57-61`)。

后果:

1. **不可见**:后台「最近事件(50)」与 /feed 对推送失败零痕迹,不翻 CF Dashboard 无法察觉渠道已坏;
2. **误报已通知**:TG 分段部分失败(如 3 段只发出 1 段)时,事件仍显示「已通知」,内容实际丢失。

## 需求

1. **通道发送失败必须在后台「最近事件(50)」可见**:实时通知轮次中,TG 或邮件通道「已启用且配置完整」但发送失败(全部段失败或部分段失败)时,落一条系统级失败事件,含通道、成功/总段数、错误摘要。
2. **绝不引入重复推送**:失败事件自身不得再进入任何通知通道(防止「通知失败→告警→又失败」循环);也不做实时通知重试(维持现状:事件已落库、通知失败不重试)。
3. **修正 notified 语义**:仅当 TG 全部段送达才标记本轮 TG 事件 `notified=1`;部分失败不标,且与失败事件共同留下痕迹。
4. 周报发送失败同样落失败事件(周报门控由 engine 在 `weekly()` 正常返回后写回——发送失败被内部吞掉不抛错,门控照常标记,失败仅留可见性记录,内容不自动重发)。
5. 后台「发送测试通知」的失败结果直接带回错误摘要(替代「见日志」)。

## 非目标(non-goals)

- 不做通知重试队列 / 通道熔断 / 备用通道切换;
- 不改 source_fail(源探测失败告警)语义与阈值;
- 不给失败事件做计数聚合或趋势页(仅进最近事件列表);
- 不清理历史事件(v1 本就不清理)。

## 验收标准

- [ ] TG 通道开且配置完整、发送全失败 → events 表新增一条失败事件(suppressed=1),后台最近事件列表显示对应徽章与备注;本轮事件不标记 notified。
- [ ] TG 部分段失败(0 < sent < total)→ 同上,且失败事件 payload 含 `{sent, total}`。
- [ ] 邮件发送失败 → 一条邮件失败事件;两通道同轮都失败 → 两条(每通道一条)。
- [ ] 通道未启用或未配置 → 不发送也**不**落失败事件(不是失败,是未尝试)。
- [ ] 失败事件永不出现在实时通知 / 周报消息文本中(单测断言 eligibleForTelegram/Email 为 false;周报聚合排除)。
- [ ] /feed(带 secret)JSON 中失败事件字段完整可读。
- [ ] 删除渠道源时其事件记录仍一并删除(现有 UI 文案承诺不变)。
- [ ] `npm run typecheck` 0 错误;`npm test` 全绿,新增行为有对应边界用例(全失败/部分失败/未配置/双通道)。
